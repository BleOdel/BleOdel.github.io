Telemetry-Driven XR Intrusion Detection

Can runtime telemetry reveal attacks that conventional monitoring may miss?

I trained and compared four unsupervised models using 580,065 normal training examples. Isolation Forest achieved F1 scores of 97.35–99.01% across four offline GPU-attack datasets, with reported detection latency of 0–2 seconds from annotated attack onset to the first positive model prediction. I then integrated the selected model with an in-headset security warning for participant evaluation.

Model: Isolation Forest (benchmarked against One-Class SVM, LOF, Elliptic Envelope) Offline result: 97.35–99.01% F1; 0–2 s detection latency across four attack datasets

The pipeline

A telemetry pipeline extracts 20 signals from the VR session, including frame-duration statistics, framerate entropy, head-rotation interval (HRI) metrics and head pose. Principal Component Analysis was used to identify the most informative of these, leaving five selected features: frame duration, maximum frame duration, frame-duration standard deviation, head-rotation interval and maximum head-rotation interval. The model was trained on 580,065 normal training examples and scores a three-second sliding window of these features as normal or anomalous.

Normal→ Anomalous→ Attack detected

Why unsupervised

Isolation Forest requires no prior assumptions about the distribution of monitored parameters, which matters in a domain like VR security where there's limited existing knowledge of which telemetry signals indicate an attack. This let the model learn what "normal" looks like for a given VR system without labelled attack data.

Why Isolation Forest

I compared four unsupervised models using accuracy, F1, detection latency and error counts. Isolation Forest offered the strongest pooled F1 score in the offline evaluation, with three false positives and eleven false negatives across 810 test points, and was selected for integration with the VR warning system.

From detection to warning

I integrated the detector with a Python-to-Unity alert pipeline. Sliding-window processing reduced false-positive triggers, while transmitting positive detections only addressed delays observed when sending both normal and attack outputs. In Unity, the warning appeared on receipt of an alert and was hidden after 25 seconds without a further alert, which limited how long it stayed on screen.

Source: thesis pp. 145, 154–155. The 25 seconds is an inactivity timeout measured from the latest alert, not a delay before the warning appears.
StageBehaviour
Feature collectionA three-second sliding window collected system indicators for detection.
Prediction filteringModel outputs were represented as 0 (no attack) and 1 (attack). A size-3 sliding window processed these predictions to trigger the warning and reduce false positives.
Positive-alert transmissionThe Python-to-Unity path sent positive detections only. Transmitting both 0s and 1s had delayed the warning display.
Warning visibilityReceiving an ALERT displayed the warning. Unity hid it after 25 seconds without a further ALERT, so it did not stay visible indefinitely.
